## 一、业务理解

这个项目面向的是有具体想法、但不一定熟悉开发的人。用户可能只是想做一个收藏夹、待办清单或展示页面，更关心做出来的东西能不能用，以及后面还能不能改。

我把主要使用过程理解为：描述需求，得到一个可以操作的应用，再根据实际效果继续调整。第一次生成之后，用户往往才会发现自己漏掉了什么，或者原来的想法需要变化。因此，项目除了要支持生成，也需要保留源码、修改记录和已经录入的数据，让后续调整有一个可靠的起点。

生成过程本身也有不确定性。模型可能超时，返回的代码可能有问题，用户也可能中途离开。如果这些情况都只能重新开始，使用成本会比较高。这也是任务状态、草稿、版本和恢复能力在这一版中占比较大的原因。

目前的范围限定为小型网页应用。涉及依赖安装、任意服务端代码和外部联网的应用，还需要额外的构建环境、权限管理和运行隔离。这一版先把当前范围内的生成、修改和保存做完整。

## 二、架构上的考虑

### 1. 前后端分离

前端和后端面对的问题有所不同。前端主要处理用户输入、生成进度、应用预览和源码编辑，交互调整会比较频繁。后端负责账号、项目数据、任务执行和模型调用，需要保证权限、状态和资源使用的一致性。

基于这个区别，我把界面和业务处理分开，前端通过 API 获取状态、提交操作。这样修改页面布局或替换编辑组件时，可以尽量沿用已有业务接口；调整模型接入和任务处理时，也能减少对页面的影响。账号凭据、模型 Key 和执行额度统一由后端管理，前端只获取展示和操作所需的信息。

部署上，前端可以作为静态文件交付，后端单独提供 API。开发时也保留了同源启动方式，方便本机运行。代码目前放在同一个仓库，前后端各自有目录、测试和启动命令。后端仍是单进程服务，现阶段的规模还不需要拆成多个服务。

### 2. 区分项目、任务和版本

项目需要长期保留，一次生成任务可能成功，也可能失败；用户正在修改的草稿和已经确认可预览的版本，也可能暂时不一致。如果把它们都当成同一份“当前代码”，失败、恢复和多页面编辑时就容易互相覆盖。

因此，我把项目作为持续保存内容的单位，把每次生成作为独立任务，并为成功结果保留版本。用户可以继续编辑草稿，也可以回到已有版本；某次任务失败时，原先能使用的内容仍然保留。

应用中的数据也需要单独考虑。例如，用户只是想恢复之前的页面样式，已经添加的待办或收藏通常不应该一起消失。所以源码恢复和应用数据保存是分开的，上传的素材也不会随源码版本回退。

### 3. 把生成任务放在后端管理

生成耗时较长，页面可能刷新或关闭。如果任务状态只保存在页面里，用户回来后很难知道它是否还在执行，也无法判断要不要重新提交。

当前由后端管理任务，页面读取执行状态。中断后保留原需求和已获得的进度，恢复时再判断哪些内容可以复用。这里还需要区分用户操作和实际资源占用：用户取消任务后，可以释放其运行名额，但已经发出的模型请求可能仍在结束过程中，执行资源要等请求真正退出后再释放。

这种处理会比简单地修改一个“已取消”状态多一些约束，但能避免反复取消、重试产生过多后台请求。对于按调用计费的模型服务，这个问题也关系到实际成本。

### 4. 模型接入和扩展方式

不同用户可能使用不同的模型服务，也可能希望使用自己的 Key。项目的生成、校验、保存和恢复流程应该尽量一致，服务差异集中在接入部分处理。以后增加服务时，可以复用已有任务流程，减少每种服务各维护一套逻辑的成本。

Skill 也是按这个思路接入的。有的方法适合指导整体创作，有的只适合影响风格、架构或某个局部，所以提供了主导和局部两种插入方式。它们用于补充用户的方法，用户本次明确提出的要求仍然优先。

另外，用户可能在任务运行期间修改 Skill。为了让修复和恢复的依据保持一致，任务启动后会保留当时使用的配置，后续修改作用于新任务。

### 5. 交互上的考虑

用户不一定知道该选什么技术或应用分类，因此输入需求时没有要求先选固定的应用类型和视觉风格。能在后续修改中调整的内容，尽量留在实际使用之后再决定。

等待过程中，页面展示后台已经发生的阶段和记录；动画只承担视觉展示。保存草稿、检查失败和预览更新也分别给出反馈，避免用户把“文件已经保存”理解为“应用已经验证可用”。

需求澄清目前还没有实现。后续希望只对会影响继续实施的关键条件提问，并给出容易理解的选项，减少用户必须先掌握技术细节才能回答的问题。

## 三、目前完成的内容

目前已经实现首页、注册登录、项目空间、方案确认、生成进度和工作台。用户可以通过平台模型或自己的 Key 生成应用，继续对话修改，也可以直接编辑源码。项目文件、版本和应用数据会保存到服务端。

工作台接入了 CodeMirror，支持文件查看与上传、草稿保存、版本预览、历史恢复和源码导出。生成任务支持主动中断和恢复；校验未通过时，保留草稿和上一成功版本。模型也会结合当前项目提出两条后续优化方向，点击后作为可编辑的输入，由用户决定是否采纳。个人 Skill 库支持 Markdown/ZIP 上传、内容查看，以及项目中的主导和局部配置。

资源控制方面，单用户最多同时运行 3 个任务，另外还有全局执行、排队、平台任务额度和存储限制。界面支持浅深色、响应式布局和减少动态效果设置。

## 四、关键实现与基础考虑

### 技术选择与代码组织

前端使用原生 HTML/CSS/JavaScript，编辑器复用 CodeMirror。当前页面规模下，这样可以减少工具链配置；代码仍有依赖加载顺序的 classic scripts，后续需要继续整理模块关系。

后端使用 Python，数据保存在 SQLite，适合目前的单机部署。项目、文件、任务和版本之间存在关联写入，集中存储便于在事务中检查和提交。多实例运行时，还需要重新处理共享状态和任务调度。

代码按 `frontend/`、`backend/`、`deploy/` 和 `docs/` 组织。前端内部按页面、共享组件和 API 客户端归类；后端的模型适配、Skill、源码校验与 HTTP 层分别放在对应模块。具体目录和运行方式见 [架构说明](architecture.md)。

### 保存与预览的一致性

编辑器保存的是草稿，预览读取成功版本的源码快照。草稿经过检查后，才会生成新版本并更新预览；检查失败时显示文件和错误位置。源码修订号用于发现过期页面或构建期间的修改，避免覆盖新内容。

验证时发现过 HTML 缺少引号仍提示通过的问题，原因是原来的解析器会容错。后来补上了独立的 HTML 检查。这类检查能发现已覆盖的语法和资源问题，应用功能是否符合需求，还需要实际运行验证。

CSS 此前没有接入语法检查，缺少右花括号时也可能被保存为成功版本。现在使用 PostCSS 检查 CSS 文件与 HTML 内嵌样式，返回对应文件和行列；失败时只保存草稿，预览继续使用上一版本。检查范围是语法和结构，属性效果与实际布局仍需在浏览器中确认。

### 恢复与模型适配

任务会保存原始需求、源码上下文和完整输出检查点。恢复时优先复用已有源码；项目源码已经被改动时，拒绝直接覆盖。没有完整输出时仍需重新请求模型，当前没有实现服务商原生的 token 续传。

已接入 OpenAI 兼容接口、Responses、Anthropic、Gemini 和 Azure Responses。DeepSeek 做过真实生成与修改验证，其余协议主要使用本机模拟服务验证。实际服务的模型权限和额度仍取决于账号配置。

### 安全与资源使用

生成代码在浏览器沙箱中运行，后端不执行生成程序。项目读写检查所属账号，数据库使用参数绑定，文件和上传包检查路径、大小等限制，用户提供的模型地址也会做公网校验。

用户 Key 只保留在服务内存中，退出或重启后清除，代价是重启后需要重新连接。Skill 当前提供指令与文本参考资料，包内脚本不执行。

当前安全措施适用于单机 Demo 的已有范围。公网运行还需要上游 DDoS 防护、源站访问限制、费用硬额度和监控。当前公网入口已启用 HTTPS，应用通过本机插件托管；电脑离线或休眠时演示服务会暂时不可用。详细限制见 [安全说明](../SECURITY.md)。

### 验证情况

最近一次代码验证通过了 122 项后端测试和 13 项前端测试，前端语法检查与静态发布也已通过。自动化测试使用临时数据库和模拟模型服务，覆盖账号隔离、CSS/HTML 错误定位、文件冲突、失败后的预览保留、任务恢复、并发准入、协议适配、项目建议和 Skill 快照等路径。

浏览器中另验证过登录、应用预览、源码编辑保存、版本更新和前后端分开运行。这些验证覆盖了主要使用路径，复杂需求下的生成质量和更多运行场景还需要继续补充。

## 五、后续安排

公网 Demo 和仓库访问已开放。后续首先补充持续可用性监控、费用告警和定期数据库备份；目前的演示依赖本机在线，稳定对外运行还需要进一步安排。这样后续发现问题时，能够区分是模型、应用还是部署环境造成的。

之后优先提高生成的可靠性，补充浏览器交互验证和关键需求澄清。目前校验更偏向源码检查，仍可能出现代码可解析、操作不符合预期的情况，这部分会直接影响使用结果。

随着项目继续扩展，再整理前端模块依赖和后端较集中的业务编排。多实例调度、团队协作，以及 npm 工程或服务端代码生成，会根据实际需求安排；其中涉及的共享限流、任务队列和运行隔离需要先设计清楚。邮箱验证和密码找回也尚未完成。
